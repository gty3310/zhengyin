# zhengyin · 古文正音 CLI

给 **AI Agent** 用的古文 TTS 预处理器：输入一篇古文（可选附每字拼音），
输出一份可直接送 TTS 的文本——其中每个字按字典默认读音读出来就是目标
读音，且凡字典里有义项映射的（通假、破读），尽量换成本字做到**音义双合**。

查不到、定不了的字，工具**不猜**：它把问题（带上下文与候选）写成
`questions.json` 并以退出码 2 停下，由 Agent 拿去问用户；用户的答案必须
通过算法的发音校验，才会被学下来并继续转换。AI 只许提议，算法负责裁决。

代码 MIT 许可证；字典数据在独立的
[zhengyin-dict](https://github.com/gty3310/zhengyin-dict) 仓库（代码与数据
分离，见下方「设计原则」第 7 条）。

## 安装

```bash
pip install git+https://github.com/gty3310/zhengyin
# 或克隆后： pip install -e .
```

要求 Python ≥ 3.9，**只依赖标准库**。

## 快速开始

```bash
zhengyin data fetch            # 从 zhengyin-dict Release 下载字典数据库（sha256 校验）
zhengyin data status           # 查看本地数据版本

zhengyin convert lunyu.txt -o lunyu.tts.txt \
    --pinyin lunyu.pinyin.txt \  # 可选：每字一个音节，空白分隔，带调符号或数字调均可
    --changes changes.json \     # 可选：逐字转换清单（可审计）
    --with-pinyin                # 可选：另出逐句拼音对照 TXT
```

拼音文件与正文**逐字对齐**（只数汉字，标点自动跳过）；数量不符会明确报错
（退出码 1）。不给拼音也可以：工具用词组表、通假/破读条目与异读语境定音，
定不了的进问答回路。

## 命令一览

| 命令 | 作用 |
|---|---|
| `zhengyin data fetch` | 下载字典数据库到 `~/.zhengyin/data/` 并校验 sha256 |
| `zhengyin data status` | 显示本地数据版本、条数与学习层条数 |
| `zhengyin convert 输入 -o 输出 [选项]` | 转换一篇古文并终检（选项见上；`--db` 可直指 db 文件；默认同时出纯文本版与 SSML 版＋钉音清单＋`audit.json`，`--ssml/--ssml-hints` 可改路径；`--rulings 文件` 预置组裁决；`--audit 文件` 改终检报告路径；语义待确认写 `semantic_questions.json`、不挡退出码；替字提案写 `substitute_proposals.json` 并以退出码 2 停下，`--substitute-review 文件` 回语境审结果） |
| `zhengyin audit 成品 --pinyin 拼音文件` | 对既有成品单独终检复检：报四类计数与未锁定明细，写 `audit.json`；全字锁定退出码 0，有未锁定项退出码 2（可带 `--ssml-hints` 标出钉音位置记 C 类） |
| `zhengyin lookup <字>` | 查一个字的全部读音、默认读音、通假条目（含义项）、破读条目 |
| `zhengyin learn export [-o 文件]` | 把本地学习层导出为字典仓格式 JSONL，供提 PR 回流 |

## 给 Agent 的使用说明

### 退出码语义

| 退出码 | 含义 | Agent 应做什么 |
|---|---|---|
| 0 | 转换完成且**终检全过**（成品每字锁定：A／C／落 A 的校验替字；或命令成功） | 取走成品（合成请用 SSML 版）；如带 `--changes` 可复述换了哪些字；`semantic_questions.json` 若有，只转交用户确认语义，不必等它 |
| 2 | 转换暂停：声音层有**残余问题**，或有**未审替字提案** | 读 `sound_questions.json`（只含无目标音可定／未知字无锁定读音／映射冲突），由 Agent 逐条作答（替字或 `"ssml"`；声音层没有 keep），写入 `answers.json` 后带 `--answers` 重跑同一命令、循环至终态；若停在提案（`substitute_proposals.json`），逐条核对替字大意是否合该句语境，写审结果（approve 须带 `sense_fit` 理由）后带 `--substitute-review` 重跑 |
| 1 | 错误（拼音数量不符、无字典数据、下载失败等） | 看 stderr 的错误信息处理，不要重试同一命令碰运气 |

### questions / answers 协议

`questions.json` 是数组，每条：

```json
{
  "id": "q7",
  "char": "說",
  "index": 8,
  "sentence": "學而時習之，不亦說乎",
  "prev": "",
  "next": "",
  "target_reading": "yue4",
  "reason": "通假多义项竞争：說 读 yue4 时可通 悦（…）、閲（看），上下文不足以定夺",
  "candidates": [
    {"char": "悦", "reading": "yue4", "sense": "唯独喜欢；拥戴悦服；喜悦", "note": "破读未核"},
    {"char": "閲", "reading": "yue4", "sense": "看"}
  ]
}
```

- `id` 按汉字序号生成（`q<序号>`），同一输入多次运行保持稳定；
- `target_reading` 是已锁定的目标读音（可能为 `null`，表示读音本身也未定）；
- `candidates` 是算法给出的候选（本字＋义项），用户也可以回答候选之外的
  任何现代汉字——算法只校验发音，不限制选字；
- 答案文件格式：`{"q7": "悦"}`（问题 id → 单个汉字）。

**分组问题（v0.3.0）**：同一（字＋目标读音）的多处待裁问题合并为一个
组问题——`id` 取组内首个出处的问题 id，另带 `"group": true`、
`"group_key": "好|hao4"`、`"occurrences"`（每处 `{id, index, sentence,
prev, next}`），`reason` 注明本组共 N 处。组问题的答案除单个汉字
（全组落字）外，还可为字符串 `"ssml"`（全组钉音：保留原字、由 SSML
标注读音）或 `"keep"`（全组保留原字、读音记为目标音、不产生转换
记录）；以组 id 或组内任一 occurrence 的 id 作键都认。组裁决写入
学习层组记录（`scope="group"`），同（字＋读音）再遇直接应用、不再
提问；也可以用 `--rulings rulings.json` 在转换前预置组裁决——格式
`{"rulings": [{"char": "謙", "reading": "qie4", "action": "ssml"}]}`，
`action` 为 `substitute`（须带 `substitute`、先过答案校验、不过
退出码 1）/`ssml`/`keep`，写入组记录时 `src` 记为 `user-ruling`。

**v0.4.0 路由改定**：分组提问不再用于声音问题——读音已锁定的
B/D 一律由终检闭环自动解决（见下「转换政策要点」的终检条），
不产生组问题；组裁决（`--rulings` 与学习层组记录）作为**用户裁断**
继续优先执行。分组形态保留在两处：声音层残余问题
（`sound_questions.json`，由执行 Agent 答）与语义待确认组
（`semantic_questions.json`，见转换政策要点）。

**校验规则**：答案字的读音必须包含目标读音、且其**默认读音恰为目标读音**
（否则 TTS 仍可能读偏）；`target_reading` 为 `null` 时，以答案字自身的默认
读音为目标。校验不过，该问题会带着失败原因重新出现在 `questions.json`
里（仍是退出码 2）。校验通过，答案写入本地学习层
（`~/.zhengyin/learned.jsonl`，标记 `user_confirmed`），同一语境再遇直接
套用、不再提问。

### 完整示例（一轮问答）

```bash
# 1) 无拼音转换《论语》首句 —— 說 的读法定不了，停下提问
$ zhengyin convert lunyu.txt -o out.txt
{"status": "questions", "questions_file": "questions.json", "question_count": 1, ...}
# exit code 2；questions.json 里是上面那条 說 的问题

# 2) Agent 拿 sentence 与 candidates 问用户，用户答「悦」
$ echo '{"q7": "悦"}' > answers.json
$ zhengyin convert lunyu.txt -o out.txt --answers answers.json
{"status": "ok", "output": "out.txt", "changes": 1}
# exit code 0；out.txt = 學而時習之，不亦悦乎，且这一映射已进入学习层
```

若同一句附上拼音（`說` 标 `yue4`），则读音由用户锁定，工具会用破读条目
的语境在通假候选间消歧，直接得出「悦」而不再提问——拼音是用户对读音的
断言，未核条目只作旁证、不单独作定音依据。

## 转换政策要点（算法细则摘要）

- **定音优先级**：学习层 ＞ 用户拼音 ＞ 词组表最长匹配 ＞ 审音表异读
  （例句语境匹配）；单音字取其唯一读音。
- **替换优先级**（v0.3.0）：用户拼音锁音（定音）＞ 学习层语境精确
  命中 ＞ 学习层组裁决（字＋读音）＞ 指定替字（prescribed）＞ 通假
  换本字（须验本字默认读音＝目标读音）/ 已核破读指定的本字 ＞ 同音
  安全替字（单音字、默认读音即目标音、按常用度取）。
- **通假的语境门**：目标读音＝原字默认读音时，通假条目只在其例句与当前
  句子语境吻合时才进入替字流程——通假记录多是特定篇章里的用法，常见字
  （如「在」「民」）在普通语境下不应被冷僻通假误伤。目标读音≠默认读音
  时，特殊读音本身就是特殊用法的信号，按义项规则走提案（v0.4.1 起
  通假不再自动落字，见下「替字语境审」条）。
- **替字语境审（v0.4.1）**：一切替字来源——通假条目（含原「互证自动
  落字」路径，已整条废除）、已核破读替字、替字索引候选（经
  `--answers` 提出时）、`--answers` 给出的替字答案——落字前都过
  两道闸：(a) 硬验（算法）：字典候选须过 `strict_substitute_ok`
  （非多音字且唯一现代读音＝目标音），答案须过答案校验（默认读音
  ＝目标音）；不过者记入驳回轨迹、永不进提案。(b) 语境审（AI）：
  过硬验的替字先生成提案 `substitute_proposals.json`（含字、读音、
  候选、来源、义项、出处与所在句上下文），convert 退出码 2、不出
  成品；执行 Agent 逐条判断「大意是否合该句语境」，以
  `--substitute-review` 回审结果——approve 必须写明 `sense_fit`
  理由，复验硬闸后落字且转换清单带 `sense_fit` 留痕；reject 改
  SSML 钉音保原字，驳回理由以 `context_review` 记入 `audit.json`
  的 `substitute_reviews` 段。**免审直落只有两类**：学习层已有
  用户确认的（字＋读音＋义项）条目（含 `--rulings` 组裁决）、
  prescribed 指定替字。无合格替字或语境审不过，一律回退钉音。
- **未核破读**：`verified` 未达已核的破读条目永不直接落字；它只能在提问
  时作候选，或在读音已被用户拼音锁定时作语境旁证在通假候选间消歧
  （消歧过程记入转换清单）。
- **提问触发**：没有定音依据时，仅当存在破读条目、非默认读音下多本字
  竞争、或条目例句与语境吻合等「特殊用法证据」才提问；仅有一条冷僻
  通假记录不构成提问理由，未决时按默认读音保留原字。
- **指定替字（prescribed）**：字典 `prescribed` 表是人工指定的替字
  （字级＝单字键、短语级＝多字键，reading 与键逐字对齐，如 緡
  mian2→绵、於戲 wu1 hu1→嗚呼）；短语级先在全文汉字序列上匹配，
  凡某字已定目标读音与条目读音冲突，整条跳过；命中逐字落字、清单
  记 `via="prescribed"` 与条目出处。旧库无此表时视为空表。
- **SSML 钉音（pin）**：保留原字不换，改由 SSML 标注读音：转换
  清单记 `via="pin"`，钉音清单（默认输出同目录 `ssml_hints.json`，
  `--ssml-hints` 可改路径；每条含全文偏移、汉字序、原字、读音、
  所在句与片段 `<phoneme alphabet="py" ph="hao4">好</phoneme>`，
  ph 用数字声调拼音），SSML 成品（默认 `<输出>.ssml.txt`，
  `--ssml` 可改路径）与纯文本成品同行结构、仅钉音处包上该标签；
  送支持 SSML 的合成引擎即可钉准。钉音来源有三：用户组裁决、
  引擎在定音阶段的自动钉音、终检闭环的自动钉音（见终检条）。
  成品只在无声音残余问题时产出，SSML 文件同理（退出码 2 时都不出）。
- **终检（audit，v0.4.0）与终态**：写出成品前必逐字审计——按字典
  现代读音字段（`is_polyphonic`／`unique_reading`）分四类：A 铁证
  （非多音字且唯一读音＝目标音）、B 默认音（多音字、目标音＝默认
  音、未钉音）、C 钉音、D 不合格（多音字目标音≠默认音未钉音未合规
  替换／未知字／唯一读音≠目标音）。**退出码 0 等价于终态达成**：
  成品不许留未锁定的字，每字须 A、C 或经校验的非多音替字（替字
  本身落 A）。审计全轨迹写 `audit.json`（检出计数、终态计数、逐字
  明细、闭环解决记录、替字驳回记录）；停在残余问题环节时也落盘
  （对暂定成品的审计）。独立复检：`zhengyin audit 成品 --pinyin
  拼音文件`。
- **声音闭环（不问用户）**：终检检出的 B/D 按确定性规则自动解决，
  逐项记入 audit 轨迹：①与默认读音**只差声调**（同音节异调，如
  為 wei2/wei4、興 xing1/xing4）→ 自动 SSML 钉调（目标音＝默认音
  的 B 同理钉音锁定）；②**音节不同** → 默认 SSML 钉全读音（保字
  保义），仅当字典有**语义等值**映射（通假本字、prescribed 指定
  替字）且替字本身过校验（非多音字、唯一读音＝目标音）才走替字；
  映射替字验不过（如多音字当替字）→ 驳回并记轨迹、改钉音原字。
  **纯同音字（替字索引）不再是合规替字来源、不再自动落字**。
  既有学习层裁决是用户裁断，继续优先，不受此限。
- **声音残余问题（sound_questions.json）**：只有按上面规则仍定
  不了的才出题——无目标音可定（无拼音且无词组/语境证据的多音
  字）、未知字且无锁定读音、映射冲突。由执行 Agent 答题（替字
  或钉音），CLI 校验后重检、循环至终态；有残余未答即退出码 2。
  声音层没有 keep 放行。
- **语义待确认（semantic_questions.json，不挡退出码）**：替字会
  改变或可能改变语义、需人判断的组单列一单：多义项通假选义证据
  弱者（孤证、语境多义项竞争）等，每组附 AI 推荐与理由。已被多
  条互证且语境吻合的通假落字不进清单（只在报告计为已应用）。
- **锁定版以 SSML 版为准**：convert 默认同时出纯文本版与 SSML
  版。纯文本版里被钉音的字无锁（尤其音调型多音字），残余风险在
  TTS 引擎，合成请用 SSML 版。
- **分组（v0.4.0 改定）**：声音问题不再分组提问（见终检条）；
  分组形态保留于声音残余问题与语义待确认组——同一（字＋目标
  读音＋类型）合并一组、一组一答/一确认、全文落字（见上
  「questions / answers 协议」）。
- **常用读音豁免的新边界（v0.3.0 定，v0.4.0 改落点）**：常用
  读音（字典 `common_readings`，源 Unihan kHanyuPinlu）仅在
  **读音未被定音时**才保留原字。一旦目标读音已被锁定（拼音/
  词组/异读任一来源）、属常用读音且不等于默认读音，就不再
  豁免：先走通假与已核破读（替字须过 v0.4.0 终检校验），解决
  不了由声音闭环自动钉音，不再进组问题、也不落替字索引。
- **变调归一**：「一」「不」的变调（yi2/yi4、bu2）只作判定归一
  （yi1/bu4），不触发替字；保留原字时输出拼音仍写原始变调读音，
  变调属韵律层、由 TTS 自行处理。
- **通假孤证与竞争证据门**：默认读音下，本字在全表同读音条数少于
  2 条的通假属孤证，不自动落字、改走提问；非默认读音多本字竞争且
  读音由用户拼音锁定时，无条目例句与当前句吻合且旁证未命中则保留
  原字，不多余提问（无拼音时不启用此门）。
- **候选校验过滤与常用度地板**：提问候选呈出前先按答案校验同一
  标准过滤（默认读音须即候选读音），并按常用度排序；同音替字候选
  须或在 8105 表内或有字频序，二者皆无者直接跳过，宁可无候选。
- **原文不动**：任何替换只发生在输出里；`--changes` 的清单记录每个
  替换的原字、替字、读音、依据类型与条目出处，可逐条审计。

## 设计原则

> 本稿汇总 2026-11-04 用户与助理逐条议定的设计原则及理由。CLI 开工时，本稿全文并入 CLI 仓库 README 的「设计原则」章，一字不删其理由部分。

## 1、定位：给 AI Agent 用的古文 TTS 预处理器

输入一篇古文（可选附每字拼音），输出一份可直接送 TTS 的 TXT（可选带拼音）：其中每个字按字典默认读音读出来就是目标读音，且语义尽量与原文等值。

为什么：TTS 生成的古文音频屡有明显发音错误（多音字按默认音读、通假字按字面读、破读不破）。这些错误是系统性的，正适合用固定算法全量拦截——让概率性的 AI 只负责生成与提议，确定性的算法负责裁决。

## 2、AI 提议，算法裁决

查不到、定不了的字，AI 或用户给出的答案都只是「提议」：必须通过算法的发音校验（该字读音含目标音、且其默认读音即目标音，TTS 不会再读偏）才能进入成品与字典。

为什么：这样 AI 的 hallucination 就算发生也进不了最终文本；人的答案同理要过校验，错了说明原因、再问一次。

## 3、保证的边界（不夸大）

- 能保证：送进 TTS 的每个字，按字典默认读音读即目标读音——可逐字对账。
- 不保证：目标拼音本身给错（源头错，算法会忠实执行）；TTS 引擎受上下文影响的个别读偏；停顿句读与「一」「不」变调等韵律层问题。
- 逼近对最终音频的校验靠二期：合成后用 ASR 回听转写，与目标拼音逐字比对，不符的句子标出重做。

## 4、转换标准：音义双合

不只处理「发音会错」的字：凡字典里有带义项映射的条目（通假、破读、带语境的异读），都尽量转换成本字/指定替字。仅有读音数据、无义项映射的字表条目不构成转换依据。

为什么：现代 TTS 按语义组织韵律、停顿乃至多音字取舍；替字语义不通，读出来就别扭，听者也难懂。音对而义不对，只是把错误从耳朵里藏到意思里。

转换优先级：

1. 用户附的拼音锁定读音；
2. 有义项映射 → 换本字（音义双对）；
3. 纯读音问题 → 从同音安全替字中挑语义最不违和的；
4. 多义项竞争、上下文定不了 → 进问答回路，带义项选项问用户，不许猜。

## 5、义项是条目的键

通假关系以（字＋读音＋义项）为键：同字在不同义项下通不同本字，同音亦然（如「共」gōng 既通「供」也通「恭」）。每条映射须带释义与出处例句。

为什么：脱离义项的「字→字」映射在真实文本里必然选错；带义项，Agent 与用户才有依据做选择。

## 6、每条数据必须有出处，AI 生成必须标明

字典每条记录带 src（出处，细到条目级）；AI 生成/整理的条目带 gen 标记（注明模型与日期）与 verified 核验状态（未核/人工已核/用户确认）。CLI 默认政策：自动替换只用权威源与已核条目；AI 未核条目只作提问提示。

为什么：数据来自多个源头、可信度天然不同。标明出处与生成方式，使用者才能按可信度筛选；不标，错数据会以权威的面貌流传。

## 7、代码与数据分离，许可证各行其道

字典与 CLI 是两个仓库：字典只放数据（人可读格式＋打包 SQLite），CLI 只放纯代码。CLI 运行时从字典仓库拉取数据，至多内置宽松许可证层的快照；BY-SA 层（如 CC-CEDICT 词组包）一律独立成包、运行时下载，不进主字典、不打包进 CLI。

许可证方针：能多宽松用多宽松，明确允许商用——CLI 代码 MIT；字典主干优先只用宽松来源（MIT/CC0/公有领域/Unicode 许可证级），确实拼不齐时才调整字典许可证就数据。自建条目以 CC0 发布；他人数据各归原证、逐项注明。

为什么：代码与数据是独立的版权作品，程序读 BY-SA 数据不会被「传染」；分开存放，工具的 MIT 才干净成立，字典也能独立被他人复用与补条。

## 8、学习回路：越用越全

用户在问答回路中确认的映射，先存本地学习层（与基础字典分开，升级基础库不冲掉），可一键导出为字典仓库的补充文件、提 PR 回流。

为什么：文言破读、文言词组这类数据没有任何现成全库，只能靠真实使用逐条长出来；每位使用者的纠正若能回流，所有人的字典都受益——这是开源的意义所在。

## 9、原文不动，转换可审计

CLI 永不改动原文；输出除 TTS 文本外，附逐字转换清单（原字→替字、依据条目、义项、出处），任何人可核对每一次转换。

为什么：输出是为发音服务的「工作本」，不是经典的新版本；学术上必须能区分原文与加工，并能追责到条目。

## 10、数据配方（主干）

- 单字读音与默认读音、字频：Unicode Unihan（Unicode License v3）
- 通假：北京师范大学 tongjiazi-resources（MIT）
- 现代异读：《普通话异读词审音表》（1985）自拆（CC0 级来源）
- 词组消歧：宽松来源部分（逐文件溯源）＋自建文言词组表
- 文言破读：自建（种子带出处与置信度，靠学习回路增长）
- CC-CEDICT：仅作隔离的 BY-SA 数据包（运行时下载）

调研依据：《正音CLI-现有库调研-2026-11-04》

**v0.3.0 修订注（常用读音豁免为何收边界）**：v0.2.0 曾规定「目标读音
属原字常用读音即保留原字、不替不问」。但《大学》全文实跑后用户指出：
好、惡这类字根本没被处理——当拼音已经把读音锁到一个不等于默认读音
的常用读音时，保留原字等于把「读对」交给 TTS 引擎去猜上下文，这与
本工具逼近 100% 的口径（第 3 条保证边界：送入 TTS 的每个字按字典
默认读音读即目标读音）直接冲突——引擎猜对与否不可逐字对账，等于
保证落空。故 v0.3.0 收边界：豁免只留在读音未定之时；读音已锁定且
≠默认且属常用读音的字，必须经通假/已核破读裁决，裁不了就按
（字＋读音）分组提问，由用户一组答一次：替字、SSML 钉音或明示
保留（keep）——明示保留是用户的裁决，不是算法的默认豁免。另同版
引入字典指定替字（prescribed）承接已有正解、SSML 钉音承接「音对
而无义合单字可替」的字，两者都让裁决结果可审计、可复用。

**v0.4.1 修订注（替字语境审闸门）**：v0.4.0 的声音闭环解决了
「读音对不对」，但《中庸》实跑暴露了另一类系统性错误：通假条目
只验「条目存在＋读音对」就自动落字，不验义项与句子语境是否
对位——地 dì→第（义项是副词「但、只」，文中全是名词「天地」）
×16、強 qiǎng→襁（义项「襁褓中抚养」，文中是「子路問強」）
×12，另有王→旺、藏→臟、稱→趁、度→剫数处，全是音对义错。
用户据此定新规：AI 找替字必须同时满足三条——非多音单音字、
读音＝目标音、大意合该句语义语境；三者缺一不许落字，拿不准
就 SSML 钉音保原字。故 v0.4.1 把通假降为**提案**：算法验音
（硬闸）、AI 审境（语境审）并留痕，审不过回退钉音；只有学习层
已确认条目与 prescribed 这两类「人已经裁过」的映射免审直落。
这与第 4 条「音义双合」同向：义合与否从此不再靠条目互证推定，
而是逐条对着句子审。

**v0.4.0 修订注（终检关与裁决分工）**：v0.3.0 把「读音已锁定但
算法定不了」的字交给用户分组裁决（替字/钉音/keep）。实跑中用户
改定分工：**声音问题不烦用户**——那本质是确定性的发音锁定问题，
应由「AI 提议＋算法校验」闭环解决；用户的时间只花在真正的语义
判断上。故 v0.4.0 设终检关：成品交付前逐字按现代读音字段核验
（A/B/C/D 四类），**退出码 0 等价于终检全过**——每字或 A（非
多音字唯一读音对上）、或 C（SSML 钉音）、或经校验且本身落 A 的
语义等值替字；B/D 由闭环自动钉音或校验替字解决（只差声调钉调、
音节不同钉全读音、映射替字验不过驳回改钉音，逐项留轨迹），
纯同音替字索引退出自动落字，声音层废除 keep。只有真正定不了
的残余（无目标音、未知字无锁定音、映射冲突）才出
sound_questions 给执行 Agent 答；语义层面的待确认（通假选义
证据弱者）另立 semantic_questions 一单、不挡退出码。锁定版以
SSML 版为准，纯文本版注明残余风险——这与第 3 条保证边界同向：
保证不靠引擎猜，靠逐字可对账的锁定。

## 数据来源与许可证

- **代码**：MIT（见 [LICENSE](LICENSE)）。
- **字典数据**：不随本仓分发。`zhengyin data fetch` 从
  [zhengyin-dict](https://github.com/gty3310/zhengyin-dict) 的 GitHub
  Release 下载，各表数据各归其源许可证（单字读音 Unicode License v3、
  通假数据 MIT、审音表为公共规范文本、自建破读种子 CC0），详见该仓
  `SOURCES.md`。本仓代码读取这些数据不改变其许可证，商用时请一并遵守
  数据侧的署名等要求。
- **字形变体归一表**（`src/zhengyin/data/variants.json`）：由 Unicode
  Unihan 的 `Unihan_Variants.txt`（kSimplifiedVariant / kTraditionalVariant
  / kZVariant）派生，仅用于把繁/简/异体字形视为同一字查表，不含字典
  内容；遵循 Unicode License v3。重新生成：`python3 tools/make_variants.py`。
- **学习层**是你本机的数据（`~/.zhengyin/learned.jsonl`），不随代码仓
  分发；`zhengyin learn export` 可把它导出提 PR 回字典仓，导出条目按
  字典仓的贡献规则（须带出处）处理。
